# Досье инженера: Профиль когнитивных и архитектурных паттернов

## 🎯 Профиль студента
- **Текущий фокус:** Сервис сокращения ссылок и аналитики кликов (TinyURL & Analytics Service). Освоение асинхронного бэкенда, кэширования (Redis Cache-Aside, Rate Limiting), брокера сообщений (RabbitMQ / aio-pika / AMQP) и мультиконтейнерной контейнеризации (Docker Compose).
- **Целевой грейд и уровень погружения:** Junior / Junior+ (первое знакомство со стеком: базовое понимание сути и назначения механизмов, без низкоуровневых кишок протоколов и распределенных систем).
- **Сильные стороны:** Уверенная рабочая база Python 3.12, FastAPI, SQLAlchemy 2.0, PostgreSQL. Базовые примитивы Redis (GET, SET, экспирация). Концептуальное понимание контейнеризации.

## 🧠 Подтвержденный багаж знаний (Освоенные темы и API)
- [x] **FastAPI: Асинхронный vs синхронный контекст исполнения:** Блокирующий вызов в `async def` блокирует весь Event Loop процесса; синхронные `def` роуты выносятся FastAPI в отдельный рабочий поток (asyncio.to_thread).
- [x] **PostgreSQL: Гарантия уникальности при конкурентной записи:** Гарантия уникальности на уровне СУБД через уникальное ограничение и перехват `IntegrityError` на уровне приложения.
- [x] **Конфигурация: Стоимость I/O в BaseSettings:** Создание каждого нового инстанса `BaseSettings` производит дисковое чтение файла `.env` и парсинг переменных, что требует обязательного кэширования через `@lru_cache`.
- [x] **Python & Linter B008: Семантика аргументов по умолчанию:** Вычисление дефолтных аргументов функций происходит один раз при их объявлении/импорте в рантайме Python; `fastapi.Depends` используется как декларативный маркер DI фреймворка, требующий исключения в flake8-bugbear.
- [x] **Docker Networking: Встроенный DNS-резолвер:** В пользовательских сетях Docker поднят DNS-резолвер на `127.0.0.11`, динамически сопоставляющий имена сервисов с IP-адресами контейнеров в сети.
- [x] **Docker Storage: Изоляция прав доступа в томах:** При bind mount сохраняются права `UID/GID` каталога на хосте, вызывая конфликт при несовпадении с `UID` процесса внутри контейнера; `named volume` изолирует данные в `/var/lib/docker/volumes` и управляется Docker с выставлением владельца под процесс.
- [x] **B-tree: Правило левого префикса в составных индексах:** Записи в узлах составного B-tree упорядочены строго по ведущему столбцу (`link_id`), поэтому фильтрация по второму столбцу (`clicked_at`) без первого исключает эффективный бинарный поиск по дереву.
- [x] **СУБД: Server Default vs Client Time:** `server_default=func.now()` исключает рассинхронизацию временных рядов из-за дрейфа часов (clock drift) между независимыми нодами/контейнерами приложения, обеспечивая единый источник времени на сервере PostgreSQL.
- [x] **SQLAlchemy: expire_on_commit в асинхронном контексте:** При коммите сессии состояние объекта переводится в `expired`, а его `__dict__` очищается (объект не удаляется из памяти, так как удерживается ссылками в коде и `IdentityMap` сессии); последующее обращение к атрибутам модели (например, при Pydantic-сериализации) провоцирует неявный I/O запрос к БД, вызывая в асинхронном рантайме ошибку `MissingGreenlet`.
- [x] **SQLAlchemy: Жизненный цикл пула соединений (QueuePool vs NullPool):** `QueuePool` удерживает базовые соединения открытыми для переиспользования, закрывая перегрузочные соединения после спада нагрузки и отправляя запросы сверх лимита в очередь ожидания; `NullPool` закрывает соединение сразу после выполнения запроса, предотвращая удержание тяжелых блокировок миграционными скриптами.
- [x] **SQLAlchemy: pool_pre_ping:** Предварительная проверка жизнеспособности соединения отправкой тестового `SELECT 1` перед выдачей клиенту ценой дополнительного сетевого запроса к СУБД.
- [x] **SQLAlchemy: Механика flush() vs commit():** При `flush()` в открытую транзакцию СУБД отправляются команды INSERT, UPDATE, DELETE и немедленно срабатывает проверка уникальности в момент вставки данных, а при `commit()` транзакция фиксируется; при сбое команда `ROLLBACK` откатывает транзакцию и снимает блокировки.
- [x] **SQLAlchemy & asyncpg: Ограничение параллелизма сессии:** Соединение `asyncpg` и сессия не поддерживают одновременное выполнение запросов из параллельных корутин (`cannot perform operation: another operation is in progress`); синглтон-сессия приводит к разделению `Identity Map` и коллизиям commit/rollback между независимыми запросами.
- [x] **CSPRNG vs PRNG (secrets vs random):** Генератор `random` предсказуем (детерминирован), в то время как `secrets` использует криптографически надежные системные операции ОС.
- [x] **PostgreSQL: Статус ABORTED и атомарность транзакции:** При нарушении констрейнта уникальности сервер СУБД переводит транзакцию в статус ABORTED для соблюдения атомарности (ACID); до отката транзакции выполнение любых последующих SQL-команд в ней блокируется СУБД.
- [x] **Паттерн Retry в Unit of Work:** При коллизии уникальности повторная попытка вставки требует открытия новой изолированной транзакции/сессии, так как в рамках упавшей транзакции СУБД отклоняет запросы.
- [x] **Pydantic v2: from_attributes (GetterDict / getattr):** По умолчанию Pydantic ожидает словарные структуры данных; флаг `from_attributes=True` переключает чтение полей на протокол атрибутов (getattr/GetterDict), позволяя валидировать ORM-модели и датаклассы.
- [x] **HTTP RFC 9110: Семантика статуса 204 No Content:** Статус 204 сигнализирует об успешном удалении/действии без необходимости возврата тела ответа; запрещает наличие payload в теле ответа, а заголовок `Content-Length` должен отсутствовать или быть равен 0.
- [x] **Python Runtime: sys.modules и Dual Module Problem:** Импорт одного и того же файла под разными путями порождает два независимых объекта модулей и классов в памяти процесса, что ломает проверку `isinstance()`.
- [x] **Python Logging: Архитектура Manager, loggerDict и дерево иерархии:** Фабрика `logging.getLogger` управляет деревом через синглтон `Manager` и реестр `loggerDict`, связывая логгеры по точкам через ссылки `parent`; создание логгера напрямую через `Logger()` исключает объект из реестра менеджера, обрывая доступ к обработчикам и всплытию логов к `root`.
- [x] **Starlette ExceptionMiddleware: Диспетчеризация по __mro__:** Поиск зарегистрированного обработчика исключений выполняется обходом иерархии наследования `__mro__` от конкретного класса к родительским, благодаря чему дочерние ошибки (`DomainError`) перехватываются раньше общего `Exception`.
- [x] **Безопасность API: Защита от Information Disclosure в ошибках 5xx:** Передача сырых системных исключений (SQLAlchemy/драйверов БД) клиенту раскрывает внутреннюю структуру таблиц и инфраструктуры, требуя обязательного сокрытия деталей за обезличенным сообщением `Internal Server Error`.
- [x] **HTTP Caching: Эвристическое кэширование браузера и Cache-Control:** При отсутствии явных директив браузер вправе самостоятельно кэшировать ответ редиректа; запрет кэширования через заголовок `Cache-Control` гарантирует прохождение каждого запроса к серверу для фиксации клика в аналитике.
- [x] **Starlette Routing: Линейное сопоставление и затенение путей (Shadowing):** Роутер Starlette сохраняет маршруты в порядке добавления и сопоставляет их линейно; корневой динамический сегмент `/{slug}` затеняет пути, если зарегистрирован раньше специфичных роутеров.
- [x] **HTTP RFC 9110: Семантика 410 Gone vs 404 Not Found:** Код 404 указывает на отсутствие ресурса (возможно временное), тогда как 410 Gone явно декларирует перманентное удаление ресурса, провоцируя краулеров немедленно исключать ссылку из индекса без повторных попыток обхода.
- [x] **Redis: Механика экспирации ключей (Passive vs Active Expiration):** Ленивое удаление ключа при чтении (GET/EXISTS) и фоновая вероятностная очистка (10 раз в секунду выборка 20 ключей с циклом при >25% протухших) для исключения линейного обхода всех ключей.
- [x] **Кэширование: Cache Stampede (Thundering Herd):** Риск исчерпания пула соединений БД и таймаутов при истечении популярного ключа; механизмы защиты через Singleflight (блокировка с ожиданием) и вероятностное упреждающее обновление (XFetch).
- [x] **Python datetime: Несовместимость Aware vs Naive:** Сравнение naive и aware объектов datetime вызывает исключение TypeError в рантайме.
- [x] **Python Asyncio: Жизненный цикл корутины и выполнение:** Вызов асинхронной функции лишь создает и аллоцирует объект корутины в памяти без исполнения ее тела; выполнение инициируется передачей корутины в Event Loop через await.
- [x] **Python Typing: ParamSpec (**P) в декораторах:** Захват и сохранение спецификации входных аргументов (*args, **kwargs) декорируемой функции для строгой статической типизации; типизация возврата через Awaitable[R | None].
- [x] **Отказоустойчивость: Автомат состояний Circuit Breaker:** Защита от бессмысленных сетевых запросов к упавшему сервису через состояния Closed (норма), Open (отсечение запросов при превышении порога ошибок) и Half-Open (пробный трафик по таймеру с возвратом в Closed при успехе или в Open при сбое).
- [x] **Rate Limiting: Edge Burst в Fixed Window:** Уязвимость удвоения лимита запросов на стыке двух фиксированных окон времени; учет временных меток в Sliding Window Log для устранения всплеска.
- [x] **Rate Limiting: Token Bucket vs Leaky Bucket:** Token Bucket пополняет токены со скоростью r в ведро емкостью C и допускает всплески (bursts) с возвратом 429 при опустошении; Leaky Bucket буферизует запросы в очередь размера B и обрабатывает с постоянной скоростью, сбрасывая излишки для сглаживания потока.
- [x] **Redis ZSET: Скользящее окно (Sliding Window Log) и очистка памяти:** Использование веса (score) для сортировки временных меток; активное удаление устаревших записей за пределами окна и пассивное удаление ключа по TTL для предотвращения утечек памяти.
- [x] **Отказоустойчивость: Архитектурный компромисс Fail-Open vs Fail-Closed:** Стратегия Fail-Open при сбое Redis пропускает запрос (HTTP 201) ради доступности сервиса, предотвращая полный отказ системы (в отличие от Fail-Closed).
- [x] **HTTP RFC 6585/9110: Заголовок Retry-After при 429 Too Many Requests:** Передача обязательного заголовка `Retry-After` с целочисленным временем ожидания в секундах при блокировке запроса лимитером.
- [x] **AMQP 0-9-1: Топология очередей и уровни персистентности:** Разделение долговечности на уровне сущностей брокера (`durable=True` у Exchange и Queue для сохранения метаданных при перезапуске) и на уровне сообщений (`delivery_mode=2` / PERSISTENT для сброса на диск); привязка очереди к Topic Exchange по Routing Key и флаг `exclusive=False` для конкурентной обработки сообщений пулом воркеров.
- [x] **aio-pika & FastAPI Lifespan: Архитектура двухуровневых пулов и Graceful Shutdown:** Инициализация `aio_pika.pool.Pool` в фазе startup lifespan для привязки примитивов синхронизации к активному Event Loop; детерминированный возврат каналов в пул через `__aexit__` при пробросе исключений из эндпоинта методом `.athrow()`; строгий порядок shutdown: закрытие пула каналов (`Channel.Close`) перед разрывом физического TCP-соединения во избежание потери данных и ошибок `ChannelClosedByBroker`.
- [x] **FastAPI BackgroundTasks & Event Loop:** Асинхронные задачи исполняются через `await self.background()` в общем Event Loop строго после отправки байтов ответа клиенту по ASGI протоколу, не задерживая возврат редиректа.
- [x] **AMQP & aio-pika Pool: Изоляция сбоев каналов:** При ошибке брокер закрывает конкретный AMQP-канал; пул каналов изолирует сбои между параллельными корутинами, предотвращая отказ всего приложения.
- [x] **Отказоустойчивость: Graceful Degradation брокера:** Сохранение доступности основного функционала (редирект 302) ценой потери второстепенных аналитических данных при падении брокера; отказ от Fail-Fast ради доступности сервиса.
- [x] **Обработка исключений: Изоляция AMQPError vs слепой except:** Перехват точечных ошибок протокола и брокера `(AMQPError, TimeoutError)` исключает маскировку логических багов приложения (например, ошибок сериализации данных) под инфраструктурные сбои.
- [x] **Observability: Структурное логирование инцидентов:** Фиксация сбоев на уровне `ERROR` с параметром `exc_info=True` для сохранения полного стека вызовов и бизнес-идентификатора (`link_id`) для расследования инцидентов.
- [x] **Архитектура Worker: Процессная изоляция от Web API:** Вынос консьюмера в отдельный процесс ОС исключает конкуренцию за общий Event Loop с HTTP-запросами и блокировку сервера; предотвращает неуправляемое умножение консьюмеров и исчерпание лимитов соединений при масштабировании веб-инстансов.
- [x] **aio-pika: Отказоустойчивость `connect_robust`:** Автоматическое восстановление соединения с периодическими повторными попытками; восстановление открытых каналов, передекларация топологии (exchanges, queues, bindings) и возобновление работы консьюмеров после сбоя сети/рестарта RabbitMQ.
- [x] **Python asyncio: Механика `asyncio.Event` и список `_waiters`:** Вызов `wait()` регистрирует ожидающую корутину в очереди `_waiters` и отдает управление в Event Loop без холостой нагрузки на CPU; вызов `set()` переводит флаг в `True` и планирует возобновление корутин на следующей итерации цикла событий.
- [x] **AMQP QoS: Управление буферизацией через `prefetch_count`:** Ограничение числа неподтвержденных сообщений (unacked) у консьюмера; устранение «эффекта жадины» при дефолтном безлимите (`prefetch=0`) и балансировка задач между воркерами.
- [x] **RabbitMQ Delivery Guarantees: Auto-ACK vs Manual ACK:** В режиме `no_ack=True` сообщение удаляется из брокера сразу из `Ready`, минуя `Unacked`, что ведет к потере данных при сбое; ручной ACK удерживает статус `Unacked` и гарантирует возврат сообщения в `Ready` при обрыве соединения.
- [x] **RabbitMQ Error Handling: Опасность Poison Messages при `requeue=True`:** Возврат невалидного сообщения в начало очереди (`requeue=True`) провоцирует бесконечный цикл повторной обработки (infinite redelivery loop); `requeue=False` исключает зацикливание воркера.
- [x] **RabbitMQ Dead Lettering: Триггеры и жизненный цикл DLX:** Условия перевода сообщения в Dead Letter (NACK/Reject с `requeue=False`, истечение TTL, переполнение очереди); маршрутизация в DLX через аргументы `x-dead-letter-exchange` и `x-dead-letter-routing-key`.
- [x] **RabbitMQ Observability: Диагностические заголовки `x-death`:** Структура метаданных о сбое (имя исходной очереди, причина гибели, счетчик ретраев, временная метка, оригинальный exchange и routing keys) для аудита отбракованных сообщений.
- [x] **AMQP Protocol Invariants: Идемпотентность и неизменяемость очередей:** Запрет на динамическое изменение аргументов (`arguments`) объявленной очереди со сбоем `406 PRECONDITION_FAILED` для сохранения контрактной консистентности между активными клиентами и брокером.
- [x] **AMQP & Распределенные системы: Гарантия доставки At-Least-Once и риск дубликатов:** Фиксация транзакции в БД до вызова ACK в брокере гарантирует семантику At-Least-Once и исключает потерю данных (Data Loss); падение консьюмера в зазоре между Commit и ACK переводит сообщение из Unacked обратно в Ready и порождает дублирование при повторной обработке.
- [x] **PostgreSQL: Мультиагрегация в едином проходе (COUNT vs COUNT DISTINCT):** Вычисление скалярных агрегатов и `COUNT(DISTINCT ...)` в едином `SELECT` исполняется за один проход/сканирование данных (через аккумулятор для простого счетчика и HashAggregate/Tuplesort для дедупликации), сокращая сетевой I/O round-trip и нагрузку на буферный кэш СУБД.
- [x] **Паттерн Unit of Work: Изоляция CPU-bound вычислений от пула соединений:** Вынос тяжелой процессорной обработки (парсинг User-Agent регулярными выражениями) за пределы контекстного менеджера сессии БД предотвращает «запирание» (starvation) соединений в пуле `QueuePool` и рост задержки (latency) сервиса под конкурентной нагрузкой.
- [x] **Архитектура СУБД: Database Pushdown vs In-Memory Aggregation:** Делегирование группировки (`GROUP BY user_agent`) уровню PostgreSQL сокращает передачу сырых данных по сети до размера кардинальности множества, исключая исчерпание RAM процесса (OOM) и блокировку Event Loop длительной синхронной итерацией.
- [x] **Python Typing & Protocol: Вариантность атрибутов (Инвариантность vs Ковариантность @property):** Обычные мутабельные переменные в Protocol инвариантны для предотвращения записи несовместимого типа в атрибут переданного экземпляра; свойства `@property` без сеттера доступны только для чтения и ковариантны, гарантируя типобезопасный возврат более узких типов подтипами.
- [x] **Docker Multi-Stage & Кэширование слоев:** Раздельное копирование манифестов зависимостей (`pyproject.toml`, `uv.lock`) перед исходным кодом обеспечивает переиспользование кэша слоя установки пакетов при изменении бизнес-логики без повторной загрузки библиотек из сети; перенос готового окружения (`.venv`) из сборочного этапа (builder) в минимальный runtime-образ (`python:3.12-slim`) исключает сохранение компиляторов, заголовочных файлов и кэша пакетного менеджера, снижая вес образа на 250–600 МБ и сокращая поверхность атаки.
- [x] **Docker Compose: Механика Healthcheck и ликвидация Race Condition:** `service_started` отслеживает лишь запуск PID 1 в контейнере; окно `start_period` исключает сжигание счетчика `retries` при инициализации СУБД/брокера, а `condition: service_healthy` в `depends_on` гарантирует запуск зависимых сервисов (FastAPI, миграции Alembic) строго после готовности сетевых сокетов.
- [x] **Docker Networking: Сетевые пространства имен (netns) и Embedded DNS 127.0.0.11:** Ядро Linux изолирует сетевой стек контейнера в отдельный `Network Namespace` с собственным независимым loopback-интерфейсом `lo` (`127.0.0.1`); обращение к соседним сервисам по имени хоста маршрутизируется через пользовательскую bridge-сеть и встроенный DNS-резолвер `127.0.0.11`.
- [x] **Docker Storage: Жизненный цикл Named Volumes vs Bind Mounts:** Именованные тома размещаются в `/var/lib/docker/volumes/<vol>/_data` и управляются драйвером Docker, изолируя приложение от хостовых конфликтов UID/GID и просадок I/O виртуализации ФС; команда `docker compose down` сохраняет данные томов, в то время как `down -v` безвозвратно удаляет их.
- [x] **POSIX Signals & Docker Lifecycle: SIGTERM vs SIGKILL:** Сигнал SIGTERM (15) перехватывается процессом для проведения детерминированного завершения (Graceful Shutdown); сигнал SIGKILL (9) обрабатывается непосредственно ядром Linux без возможности перехвата или блокировки процессом; при превышении таймаута остановки (stop_grace_period, 10s) Docker принудительно посылает SIGKILL, обрывая соединения и возвращая unacked-сообщения брокера в очередь со статусом Ready.
- [x] **Asyncio Architecture: loop.add_signal_handler vs signal.signal:** Синхронный `signal.signal` прерывает поток исполнения в произвольный момент байткода, создавая race conditions при взаимодействии с примитивами синхронизации asyncio; `loop.add_signal_handler` безопасно регистрирует сигнал в очереди событий Event Loop через внутренний pipe/socketpair, гарантируя потокобезопасность.
- [x] **AMQP Consumer Lifecycle: basic.cancel и Drain In-flight сообщений:** Вызов `queue.cancel(consumer_tag)` отправляет брокеру команду basic.cancel, отсекая получение новых сообщений, но сохраняя открытый TCP-канал для завершения обработки и фиксации ACK текущих задач; аварийный разрыв соединения возвращает все unacked-сообщения обратно в состояние Ready.
- [x] **Нагрузочное тестирование & Locust: Процентили задержки (p50, p95, p99 vs Average), изоляция редиректов и потолок GIL:** Среднее арифметическое (Average) сглаживает единичные аномалии и маскирует деградацию отдельных пользователей из-за пауз GC или задержек БД; процентили p50, p95, p99 определяют порог задержки, быстрее которого получили ответ 50%, 95% и 99% пользователей соответственно; параметр `allow_redirects=False` исключает переход на целевые внешние ресурсы, изолируя замеры латентности собственного сервиса; GIL исключает параллельное исполнение потоков, позволяя только одному потоку процесса интерпретировать байткод единовременно.
- [x] **Chaos Engineering: Деградация кэша в Cache-Miss, изоляция BackgroundTasks и применение connect_robust:** Отказ Redis обрабатывается как промах кэша (Cache-Miss) с обращением напрямую в БД; рост задержек при падении кэша обусловлен поиском записей и открытием новых соединений к базе данных; исполнение задач в `background_task` после отправки ответа исключает возврат ошибки клиенту при сбое брокера; в качестве примитива отказоустойчивости соединения воркера подтверждено использование `connect_robust`.
- [x] **PostgreSQL & Asyncpg: Физика `idle in transaction`, снимки БД и закрытие соединений в `__aexit__`:** Состояние `idle in transaction` удерживает открытый снимок БД на момент создания транзакции и соединение со стороны SQLAlchemy, блокируя очистку мертвых строк (dead tuples) процессом `VACUUM` из-за риска чтения старых данных открытой транзакцией и приводя к захламлению памяти; освобождение соединения гарантируется блоком `finally` в методе `__aexit__`.
